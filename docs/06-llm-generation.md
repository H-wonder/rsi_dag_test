# 下一阶段：让 LLM 生成结构

> 2026-11-25。本文件定义“输入什么、约束什么、怎么判断做对了、哪些仍必须人工”。
> 它是挑战档要求的生成契约，不是已经跑过的实验。

## 1. 目标

把现在的人工过程：

```text
读任务 → 选模式 → 填节点 → 填参数 → 跑分 → 修
```

变成：

```text
LLM 读任务 + 工具目录 + 数据样例 + 节点 schema
  → 输出结构 JSON
  → schema 校验
  → 执行 / 打分
  → 失败则带断言差异重试
```

**LLM 只生成结构，不参与运行时的控制流**；循环、分支、终止仍由解释器执行。

## 2. 输入

| 输入 | 内容 | 来源 |
|---|---|---|
| 任务 prompt | 用户原始要求 | benchmark |
| 数据样例 | 每个 sheet 的表头 + 前 3 行；gmail/slack 的主题与摘要 | initial_state |
| 工具目录 | `api_search` 返回的 API 列表（id、method、url、请求字段） | bridge |
| 节点 schema | `schema/structure.schema.json` | 本仓库 |
| 模式库 | P1–P6 + 决策树 | `docs/03-patterns.md` |
| 示例 | 2–3 个结构（不同模式） | `structures/` |
| 约束 | 最大嵌套、最大迭代、禁止节点 | 本文第 3 节 |

不直接给全量 initial_state（太大）；给“表头 + 样例行 + 资源清单”，需要细节时 LLM 用工具查。

## 3. 约束（硬性）

1. **节点白名单**：只能用 `schema` 里定义的 12 种节点，不能发明类型；
2. **循环上限**：`maxIterations ≤ 300`，嵌套深度 ≤ 2；
3. **必须有终止**：每个 loop 至少有 `maxIterations`；while/retry 必须有 `condition`；
4. **先过滤后动作**：写操作前必须有 `filter`/`branch` 约束对象；
5. **LLM 不做控制流**：不允许 `llm` 节点决定“是否继续循环”；
6. **副作用可审计**：每个 action 要能在结果里看到参数（`collect`/`perIteration`）；
7. **schema 校验通过**才允许执行；
8. **禁止**：删除、付款、批量发信给全量用户等不可逆动作（除非任务明确要求且人工确认）。

## 4. 输出契约

```json
{
  "meta": { "task": "...", "domain": "...", "pattern": "P1..P6", "bridge": "..." },
  "nodes": [ ... ],
  "edges": [ ["start", "..."], ... ]
}
```

生成后先跑：

```bash
python3 -c "import json; json.load(open('structure.json'))"   # 语法
# JSON Schema 校验（下一步实现 validate_structure.py）
```

校验失败 → 把错误信息返回给 LLM 重试（最多 2 次）。

## 5. 判定“做对了”

| 层级 | 判定 | 说明 |
|---|---|---|
| 语法 | JSON + schema 通过 | 硬门槛 |
| 结构 | 有终止、深度 ≤2、节点白名单 | 硬门槛 |
| 执行 | `status=OK`，无异常 | 硬门槛 |
| 效果 | 官方 `partial_credit` | 主指标 |
| 解释 | 每个节点/分支能对应到任务要求 | 人工抽查 |
| 成本 | 迭代数、工具调用数 | 辅助 |

**成功标准**：held-out 任务 `partial_credit = 1.0`，且结构能被人解释；
不是“生成得像示例”。

## 6. 自动生成循环（建议实现）

```text
1. 任务分析：LLM 输出 {记录数, 维度, 是否需要分支, 是否需要汇总}
2. 选模式：按 03 的决策树，输出 P1..P6 + 理由
3. 填结构：按 schema 生成 nodes/edges
4. 校验：JSON + schema + 终止条件
5. 试跑：bridge + 后端，取 /score
6. 修复：把失败断言 + 当前结构喂回，最多 2 轮
7. 记录：结构、分数、失败原因、人工修改 diff
```

## 7. 哪些能自动、哪些必须人工

| 环节 | 自动化 | 原因 |
|---|---|---|
| 选模式 | ✅ | 由数据形态决定，规则明确 |
| 填节点/参数 | ✅ | schema 封闭，可校验 |
| API 端点发现 | 🟡 | `api_search` 可查，但结果要确认 |
| 业务规则解释 | ❌ | 规则藏在邮件/Slack/备注里，需要判断（Carol、2B-105、Pinnacle Net 20） |
| 验收标准 | ❌ | “什么算对”由断言决定，LLM 不应改 |
| 不可逆动作 | ❌ | 付款/群发需要人工确认 |
| 失败归因 | 🟡 | 可给候选原因，最终由人判断 |

## 8. 风险

| 风险 | 缓解 |
|---|---|
| 编造不存在的 API/字段 | 只允许工具目录里的 URL；执行前校验 |
| 结构能跑但语义错 | 断言 + 人工抽查理由 |
| 过度拟合示例 | held-out 迁移题；禁止复制示例参数 |
| 死循环/烧钱 | `maxIterations` + 预算 + 硬上限 |
| 把该人工的规则“猜”出来 | 结构里标注证据来源；无证据的规则要求人工确认 |

## 9. 第一步实验（建议）

1. 取 2 道 held-out（如 Zoho、Analyst 的同类新题）；
2. 给 LLM：prompt + 表头样例 + 工具目录 + schema + 2 个示例结构；
3. 要求输出结构 + 一段“为什么这样编排”；
4. 人工只做 schema 校验和一次运行；
5. 记录：首次分数、修复轮数、人工改动点。

这一步的产出不是“全自动”，而是**量化 LLM 能替代多少人工**。
